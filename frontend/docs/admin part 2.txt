ADMIN PART 2 — Quản lý sản phẩm, danh mục và import batch

Mục đích tài liệu
- Ghi lại những gì đã làm ở phần admin liên quan đến quản lý sản phẩm, quản lý danh mục và import file Excel.
- Giải thích bằng tiếng Việt, đơn giản, đi từ ý tưởng đến cách code đang hoạt động.
- Giúp đọc lại nhanh để hiểu vì sao thiết kế như vậy và khi dùng thì phải làm gì.

1. Tổng quan kiến trúc admin
- Admin của dự án này không đi theo kiểu mỗi nút là một trang rời hoàn toàn.
- Thay vào đó, dashboard admin hoạt động như một trang lớn, bên trong đổi panel bằng state.
- Vì sao làm vậy:
  - Trải nghiệm giống một hệ thống quản trị thật.
  - Sidebar đổi nội dung ngay, không phải chuyển trang liên tục.
  - Dễ giữ layout đồng nhất.

Luồng chính:
- Admin đăng nhập.
- Nếu role là ADMIN, chuyển vào dashboard.
- Sidebar đổi panel: tổng quan, sản phẩm, danh mục.
- Các form thêm/sửa hiển thị bằng Portal để nổi trên layout.

2. Quản lý sản phẩm là gì trong dự án này
- Sản phẩm trong backend có các field chính:
  - product_code
  - product_name
  - category_id
  - default_specs
  - created_at
- Khi frontend hiển thị, nó map lại thành các field dễ đọc hơn như code, tên, danh mục, thông số, ảnh.

Vì sao phải bám theo schema thật:
- Nếu frontend dùng field ảo như name/sku/price/status thì rất dễ lệch backend.
- Khi schema thật thay đổi, chỉ cần chỉnh lớp map dữ liệu và form là đủ.

3. Danh sách sản phẩm hoạt động thế nào
- Trang sản phẩm gọi API lấy danh sách sản phẩm.
- Sau đó normalize dữ liệu để hiển thị:
  - code lấy từ product_code
  - name lấy từ product_name
  - category lấy từ product_categories.category_name
  - ảnh lấy từ product_images
  - thông số lấy từ default_specs

Vì sao normalize dữ liệu:
- Dữ liệu từ backend thường có cấu trúc phức tạp hơn UI.
- Normalize giúp UI đọc dễ hơn và code render gọn hơn.
- Khi làm bảng và modal, chỉ cần dùng một dạng dữ liệu thống nhất.

4. Modal thêm/sửa sản phẩm
- Modal sản phẩm đã được làm theo kiểu riêng, nhìn giống modal quản lý danh mục.
- Có Portal để render ra ngoài layout.
- Có các ô chính:
  - Ảnh sản phẩm
  - Mã sản phẩm
  - Tên sản phẩm
  - Danh mục
  - Default specs

Cách xử lý khi sửa:
- Mã sản phẩm được đổ lại từ dữ liệu cũ nhưng bị khóa.
- Tên sản phẩm, ảnh, thông số có thể sửa.
- Danh mục cũng được đổ lại theo dữ liệu cũ.

Vì sao làm như vậy:
- Mã là định danh chính, thường không nên đổi khi sửa để tránh lệch dữ liệu.
- Tên, thông số, ảnh là phần mô tả nên cho sửa.
- Danh mục có thể đổi nếu nghiệp vụ cho phép.

5. Ảnh sản phẩm
- Form sản phẩm có phần chọn ảnh và preview ảnh.
- Ảnh được upload riêng sau khi lưu sản phẩm xong.
- Backend đã có endpoint upload ảnh riêng cho sản phẩm, nên frontend chỉ cần gửi file ảnh sau khi đã có id sản phẩm.

Vì sao upload ảnh riêng:
- Tách logic rõ ràng: tạo sản phẩm trước, gắn ảnh sau.
- Dễ xử lý hơn so với nhét cả dữ liệu sản phẩm và ảnh vào một request phức tạp.
- Backend cũng dễ kiểm soát ảnh chính/ảnh phụ.

Cách dùng:
- Chọn ảnh trong modal.
- Bấm lưu sản phẩm.
- Hệ thống tạo/cập nhật sản phẩm.
- Nếu có ảnh, hệ thống upload ảnh lên endpoint ảnh của sản phẩm.

6. Quản lý danh mục
- Danh mục có các field chính:
  - category_code
  - category_name
  - description
  - created_at
- Frontend hiển thị theo dạng bảng, có phân trang 6 item mỗi lần.
- Modal danh mục cũng dùng Portal.

Cách khi sửa danh mục:
- Mã danh mục được đổ lại nhưng khóa không cho sửa.
- Tên danh mục và chú thích cho sửa.

Vì sao khóa mã:
- Mã danh mục là khóa nhận diện.
- Nếu đổi lung tung có thể gây lệch dữ liệu liên kết với sản phẩm.
- Chỉ nên cho sửa tên và chú thích trong phần quản trị thông thường.

7. Tìm kiếm, lọc và phân trang
- Sản phẩm và danh mục đều có tìm kiếm nội bộ.
- Sản phẩm còn có lọc theo danh mục.
- Danh mục có phân trang cố định 6 dòng mỗi trang.

Vì sao có các phần này:
- Dữ liệu quản trị thường dài, không thể dồn hết vào một màn hình.
- Tìm kiếm giúp admin thao tác nhanh.
- Phân trang giúp UI gọn và dễ đọc hơn.

8. Vì sao dùng Portal cho modal
- Modal được render ra document.body thay vì nằm trong cây DOM của page.
- Điều này giúp tránh lỗi bị che bởi overflow hoặc z-index.

Hiểu đơn giản:
- Nếu modal nằm trong layout bình thường, đôi khi nó bị cắt hoặc nằm sau các khối khác.
- Portal giúp modal luôn nổi trên cùng.

Cách dùng trong dự án:
- ProductForm
- CategoryForm
- ImportBatchReviewModal
- Các popup admin đều dùng cùng kiểu này

9. Import file Excel là gì
- Import là chức năng cho phép upload file Excel theo mẫu.
- File mẫu có các cột dữ liệu cố định.
- Backend đọc file, kiểm tra từng dòng, và chia thành 2 nhóm:
  - valid: đúng định dạng
  - invalid: sai định dạng

Vì sao phải tách valid/invalid:
- Không phải dòng nào trong file cũng đúng.
- Nếu import một phát hết sẽ dễ làm hỏng dữ liệu.
- Tách ra giúp admin xem rõ dòng nào hợp lệ, dòng nào cần sửa.

10. Batch import là gì
- Mỗi lần upload Excel sẽ sinh ra một batch.
- Batch là một lô dữ liệu tạm.
- Trong batch có các dòng valid và invalid.

Ý nghĩa:
- Batch giống một phiên làm việc tạm trước khi quyết định ghi vào database thật.
- Admin có thể xem trước rồi mới quyết định approve hoặc reject.

11. Luồng import batch đang hoạt động
- Admin tải file mẫu.
- Điền dữ liệu vào file.
- Upload file lên hệ thống.
- Backend tạo batch và trả về batchId.
- Frontend mở màn hình review batch.
- Review batch hiển thị 2 khối:
  - Valid
  - Invalid
- Admin chọn:
  - Approve để lưu valid vào database
  - Reject để hủy batch và xóa dữ liệu tạm

Cách hiểu đơn giản:
- Upload là bước đưa file lên.
- Batch review là bước kiểm tra lại trước khi chốt.
- Approve là xác nhận lưu thật.
- Reject là bỏ toàn bộ lô đó.

12. Màn hình review batch trên frontend
- Sau khi upload xong, frontend mở modal review batch.
- Modal này chia rõ thành 2 cột hoặc 2 khối:
  - Dòng valid
  - Dòng invalid
- Mỗi dòng hiển thị thông tin chính và lỗi nếu có.
- Có nút:
  - Reject batch
  - Approve batch
  - Tải file lỗi

Vì sao thiết kế như vậy:
- Admin nhìn nhanh là biết file nào tốt, file nào lỗi.
- Không cần vào backend để đọc log.
- Ra quyết định rõ ràng hơn.

13. Tải file lỗi
- Nếu batch có dòng invalid, frontend cho tải file lỗi.
- File lỗi giúp admin sửa lại ngay trên Excel.

Vì sao cần:
- Không phải lỗi nào cũng sửa thủ công trong UI.
- Xuất file lỗi ra sẽ nhanh hơn khi dữ liệu nhiều.
- Sửa xong có thể upload lại nguyên file.

14. Tại sao không đụng backend mà vẫn làm được frontend
- Backend đã có sẵn endpoint cho template, upload, lấy batch, approve, reject và export lỗi.
- Frontend chỉ cần gọi đúng endpoint và hiển thị đúng dữ liệu.

Điểm quan trọng:
- Frontend không tự quyết logic nghiệp vụ.
- Backend vẫn là nơi xác thực và ghi dữ liệu thật.
- Frontend chỉ làm nhiệm vụ hiển thị và điều phối thao tác.

15. Cách gọi API trong admin service
- `getProducts` lấy danh sách sản phẩm.
- `getCategories` lấy danh sách danh mục.
- `createProduct` / `updateProduct` lưu sản phẩm.
- `createCategory` / `updateCategory` lưu danh mục.
- `downloadImportTemplate` tải file mẫu.
- `uploadImportFile` upload file Excel.
- `getImportBatch`, `approveImportBatch`, `rejectImportBatch`, `exportInvalidImportRows` xử lý batch.

Vì sao gom vào admin service:
- Dễ bảo trì.
- Không phải viết request rải khắp component.
- Khi đổi endpoint chỉ sửa một nơi.

16. Vì sao map lại dữ liệu trước khi mở form sửa
- Khi list sản phẩm/danh mục hiển thị, dữ liệu đã được normalize thành code, name, category, description...
- Nhưng form sửa cần đúng tên field backend.
- Do đó phải map ngược lại trước khi đưa vào form.

Ví dụ:
- code -> product_code
- name -> product_name
- category -> category_id
- description -> description

Vì sao cần bước này:
- Nếu không map ngược, form sẽ không hiện đúng dữ liệu cũ.
- Dễ gây nhầm lẫn khi sửa.
- Đây là nguyên nhân trước đó khiến mã cũ không hiện đúng.

17. Cách dùng cho admin
- Thêm sản phẩm:
  - Bấm Thêm sản phẩm mới
  - Nhập ảnh, tên, danh mục, thông số
  - Lưu
- Sửa sản phẩm:
  - Bấm sửa ở dòng sản phẩm
  - Mã cũ hiện sẵn nhưng khóa
  - Sửa tên, ảnh, thông số, danh mục nếu cần
- Thêm danh mục:
  - Bấm thêm danh mục
  - Nhập mã, tên, chú thích
  - Lưu
- Sửa danh mục:
  - Mã cũ hiện sẵn nhưng khóa
  - Sửa tên và chú thích
- Import:
  - Tải file mẫu
  - Điền Excel
  - Upload
  - Xem valid/invalid
  - Approve hoặc Reject

18. Lý do thiết kế theo cách này
- Giữ logic rõ ràng giữa UI và dữ liệu thật.
- Giảm rủi ro làm sai schema.
- Admin nhìn vào là hiểu ngay bước nào là tạo, bước nào là duyệt, bước nào là hủy.
- Dễ mở rộng về sau, ví dụ thêm ảnh phụ, thêm import nhiều sheet, hoặc thêm bước review sâu hơn.

19. Những phần đã ổn định hiện tại
- Quản lý sản phẩm đã có modal đẹp, có ảnh, có schema thật.
- Quản lý danh mục đã đồng bộ với backend.
- Import batch đã có review valid/invalid.
- Có nút Approve và Reject.
- Có Portal cho modal để hiển thị chuẩn.

20. Ghi nhớ nhanh
- Sản phẩm:
  - Mã khóa khi sửa
  - Tên, ảnh, thông số sửa được
- Danh mục:
  - Mã khóa khi sửa
  - Tên và chú thích sửa được
- Import:
  - Upload -> batch review -> approve/reject
  - valid lưu, invalid sửa lại hoặc reject toàn bộ

Nếu muốn, phần tiếp theo có thể viết thành 1 file riêng sâu hơn về:
- cách hoạt động của import batch valid/invalid
- cách hoạt động của Portal và modal
- cách map dữ liệu giữa backend và frontend
- cách tổ chức code admin theo panel
